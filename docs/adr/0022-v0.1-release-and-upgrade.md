# ADR 0022: v0.1 Release, Provenance, and Upgrade

- Status: Accepted
- Date: 2026-09-03

## Context

AWG release bytes become elevated installation input. The release path must preserve the public/private boundary, bind binaries to reviewed source, and avoid giving contributor-triggered public workflows repository write authority or access to a persistent workstation.

The implementation and official GitHub Actions runner package are currently verified on x86-64 Windows and Linux. Although the Go code cross-builds for Linux arm64, the v0.1 runner package and native security acceptance are x86-64 only.

## Decision

The supported v0.1 release artifacts are:

```text
awg_0.1.0_windows_amd64.zip
awg_0.1.0_linux_amd64.tar.gz
awg-control_0.1.0_linux_amd64
SHA256SUMS
```

The platform archives contain `awg`, `awg-broker`, the license, README, and the matching synthetic install specification. They contain no private workflow installation, machine configuration, credential, token, or runner package.

All binaries are built with `CGO_ENABLED=0`, `-trimpath`, the release version, and the exact lowercase 40-hex public commit. `awg version`, `awg-control version`, installed metadata, execution reports, and `doctor` expose the applicable source binding. The package script refuses a dirty tree, a source mismatch, or an existing output directory.

Release construction and publication are local trusted maintainer operations after read-only hosted CI succeeds. No public release workflow receives `contents: write`; public pull requests therefore cannot inherit a release-token path. The annotated tag, GitHub release, exact source metadata, and published `SHA256SUMS` form the v0.1 provenance record.

v0.1 does not claim independent signature or transparency-log protection. `SHA256SUMS` detects corruption and substitution relative to the release record but is served by the same GitHub release channel. Operators whose threat model includes compromise of that channel must independently pin the reviewed commit and reproduce/compare the build or defer installation.

Linux arm64 packaging and support are deferred until an official compatible runner package is pinned and native arm64 identity, IPC, filesystem, service, and process-boundary acceptance can be inspected. A cross-build alone is not a support claim.

This release-specific decision supersedes ADR 0003's initial Linux arm64 artifact requirement; it preserves ADR 0003's cgo-free build and honest native-evidence requirements.

There is no in-place or request-driven updater in v0.1. Upgrade is a fail-closed management sequence:

1. run `doctor` with the installed version;
2. use the matching old external release binary to uninstall verified owned state and control files;
3. verify the new release checksums;
4. install the new release with the reviewed specification and same private repository;
5. run `doctor` and a minimal end-to-end request.

Uninstall preserves the private repository, ledger, approved-root contents, and unrelated paths. Execution is unavailable during the transition. Drift aborts before broad mutation.

## Consequences

- Release authority stays outside public pull-request execution.
- Users can bind installed state and returned reports to an exact public commit.
- The supported matrix matches real evidence instead of the compiler target list.
- v0.1 users must perform a short uninstall/reinstall for upgrades and must understand the documented same-channel checksum limitation.
